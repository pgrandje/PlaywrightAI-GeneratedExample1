# CoPilot-Only AI-Generated Simple Playwrite Test Suite

## Overview:
This suite is a simple Playwright test suite example that was used to examine whether an entire test framework and test suite could be generated using GitHub CoPilot.  It was a simple experiment to determine where an AI LLM could be used for efficiency gains versus coding the tests directly.  In this example the Playwright MCP agents were not used.  

No code was directly touched in the project other than this README file. All code was written from prompts passed to CoPilot.

## Goal
The goal was to 
- Build an example test suite that demonstrated best-practices and readability.
- Followed Page Object Model principles with all browser interactions contained in readable page object classes that corresponded to the pages in the application under test.
- Used symbol names that would be easy to read for another engineer who did not develop this code.
- Uses fixtures where appropriate
- Demonstrate examples of intercepting an API and running assertions on either the outgoing payload or incoming response.
- Used meaningful assertions with meaningful failure messages throughout the test suite.
- Have easy to read tests that mirrored user actions/workflows by calling readable page object methods that mirroed those user actions.

## The Application Under Test
For this example the tests run against a simple, public-facing, photography website:  paulgrandjeanphotography.com.
No authentication is necessary to use this site.  Authentication support within fixtures will be demonstrated in a later example project to be developed in a different repository.  This example is intended as my first AI, test-generation experiement.

## Methodology
GitHub CoPilot, the free version, was used to generate this code.  All code was generated by prompting CoPilot; that is, the code was not touched.  The only part of the project that was directly manipulated by the engineer (myself) was this README file.  The code was however reviewed after each prompt-response interaction.

Note that a commit does how MCP agents were added but that was for learning purposes after the test suite was built and tested.  The agents were then removed with a following commmitfor consistency with the goals of this repo.

## Prompts Used
Severy very explicit prompts were required.  For example, 
- I made clear page object must be used for all browser interactions.
- I had to tell the AI to rename page object method names to match user actions.
- I explictely told it which tests to create for covering specific user cases.
- I had to tell it the folder structure and folder names.
- Supplied very explicit instructions for the tests such as, 
- Open page X
- Verify the page using the text header
- Write tests for all main menu items, etc.  
- Only use Chromium and not other browsers
- Comment out the Firefox and Webkit configuration
- Fix the Locators to match a standards I was expecting
- Fix some errors flagged by the editor

## Conclusion
Essentially, I had to tell it everything; to the point where it probably didn't save much time had I coded the tests and page objects directly.

I'm saying this though with some caveats.
- Using Playwright's MCP Agents likely would have eliminated some of the explicit instructions of what to test.
- Establishing a template of instructions such as "use page objects for all browser interactions" and "write fixtures for instantiating page objects" and "name page object methods according to user actions taken against  the app" could have eliminate a lot of the back-and-forth with the chat-client.

As a learning exercise this was helpful to see what GitHub CoPilot could do by itself.  It was still impressive in that it could read the application and generate test cases by itself.  This exercise also served to discover what MCP brings to test case generation.
